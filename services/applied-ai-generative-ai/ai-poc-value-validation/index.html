A PoC exists to produce a decision, not a demo#

Four weeks, instrumented end to end, ending in a fund/kill verdict with named owners

A PoC exists to produce a decision, not a demo. Four weeks, one metric, a real data path, and a written kill-or-fund verdict with the evidence attached. The discipline is saying no fast: most ideas die at the provability screen, and that is the program saving money.

The sprint is engineered backwards from the exit report. Baseline collection starts on day one, the eval set is built before the model is touched, and the final deck is one page of numbers your CFO can audit against the ledger.

Below is the anatomy of the sprint: the failure modes that turn PoCs into demo-ware, the reference architecture for a four-week evidence machine, and the gates the verdict must clear.

No baseline to no verdict owner — how PoCs become demo-ware#

No baseline, no real data, no integration probe, no verdict owner — and the fix for each

Each failure here is a shortcut taken in week one that costs a program in month six — the countermeasures are cheap, and none of them is optional in this sprint.

The four-week evidence machine: canvas, data path, eval set, probe#

Canvas, data path, eval set and probe arranged to produce decision-grade evidence

The architecture is sized for four weeks: one baseline, one metric, one real data path, one verdict. Everything that does not serve the verdict is explicitly out of scope, and the out-of-scope list is written at kickoff.

The sprint path — from kickoff to verdict#

Week-by-week instrumentation, from canvas signing to gate reading

Week-by-week flow from baseline signing through data-path construction to the verdict review — including the mid-sprint checkpoint where weak ideas are killed early and cheaply.

Verdicts, not velocity — what the sprint scoreboard shows#

Delta, unit cost and integration gaps as the standing scoreboard

Sprints run, verdicts on time, ideas funded to production, ideas killed on evidence and baselines signed — the record that shows whether the sprint process is producing decisions or theater.

The default sprint stack, and where we sign deviations

Sprint governance — production-grade data handling in miniature#

The data controls a four-week sprint still carries

Sprints run under the same data governance as production: consent, PII handling and access are inherited from your estate, so the verdict is admissible in the steering meeting that counts.

  • Metric freeze

    Threshold changes require a new sprint, not a quiet edit

  • Real-data rule

    Exit reports must cite runs on production-shaped data

  • Access expiry

    Sprint credentials die with the sprint

  • Verdict integrity

    Both verdicts use the same report format; kills are celebrated in the ledger

Kill verdicts get the same evidence pack as funded ones — the auditable record of why an idea died is the asset that keeps the next portfolio honest.

A PoC verdict is an instrument reading#

The measurement discipline that makes a four-week verdict defensible in a steering committee

Most PoCs measure the wrong thing: demo delight instead of decision-grade deltas. The sprint is instrumented from day one — a provability canvas fixes the metric, the measurement method and the baseline before any model runs; baseline collection measures the human work the model would replace (minutes per case, error rates, rework shares); and the real data path runs production-shaped data under production-shaped governance, so the verdict survives contact with the estate. An integration probe touches at least one real system, because the honest friction — auth, schemas, latency — is where PoC timelines actually die.

The fund/kill gate is the product. At week four the steering committee reads three numbers: delta against baseline on the golden set, cost per unit of work at sprint scale, and the integration gaps with named owners. Fund means a funded delivery slice with a metric; kill means a documented kill reason in the ledger — and both are wins, because the cheapest failed project is the one that costs four weeks.

  • Provability canvas first

    Metric, method and baseline signed before a model runs.

  • Real data path

    Production-shaped data under governance; synthetic only where PHI/PII forbids.

  • Integration probe

    One real system, early — friction is evidence, not noise.

  • Fund/kill with named owner

    Three numbers at the gate; kill reasons logged like fund decisions.

  • Why four weeks — is that realistic for a real verdict?

    Four weeks is enough because the sprint is bounded deliberately: one provable slice, a signed baseline, a real data path and a named verdict owner. Ideas that cannot fit that box fail the provability screen before they consume a sprint.

  • What if the data is not ready in week one?

    The data path is a week-1 gate, not a hope: if the data cannot be wired and profiled by the end of week one, the gate kills the sprint and returns the finding — data readiness is a verdict, not a slide.

  • How do you measure value without a production deployment?

    The baseline is signed before week one ends, so the eval set measures delta against a number your finance team has already countersigned — holdout-adjusted, with the measurement method in the verdict pack.

  • Do we get to keep the code and eval artifacts?

    Yes. Baseline, golden eval set, cost model, integration gap list and the verdict pack are yours at verdict time, whatever the verdict is — a kill still leaves you the instrumented evidence.

  • What makes this different from our innovation team running a pilot?

    The gates. A pilot runs on enthusiasm; the sprint runs on kill criteria with named owners, and the fund gate requires a price, a data path and an integration probe — the same evidence a steering committee will ask for at scale.
